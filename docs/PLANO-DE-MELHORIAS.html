Projeto SharkTech

Roadmap de evolução para um projeto de portfólio robusto, organizado e pronto para produção.

Repositório: Igor-Danton/Projeto_SharkTech

Data da análise: 30/09/2026

Escopo observado: src/, public/, database/, docs/, package.json e configurações de ambiente.

Objetivo: priorizar qualidade, segurança, testabilidade, manutenção e evidências de engenharia para recrutadores.

1. Sumário executivo

O projeto já possui uma base coerente: separa o servidor de public/, usa pool MySQL, consultas parametrizadas, bcrypt, sessão HTTP-only, documentação de instalação e SQL versionado. A próxima etapa não é reescrever tudo, mas transformar essa base em um sistema verificável e sustentável.

Prioridade 1 — Segurança de configuração e autenticação.
Falhar rapidamente quando segredos estão ausentes, remover o fallback de SESSION_SECRET, adicionar rate limiting no login, validar entradas com esquema e definir políticas de sessão/CSRF.
Prioridade 2 — Qualidade automatizada.
Adicionar ESLint, Prettier, testes unitários/integrados e GitHub Actions. O projeto deve impedir que código sem lint ou sem testes passe despercebido.
Prioridade 3 — Separação de responsabilidades.
Manter rotas finas e mover validações, regras de negócio e acesso a dados para controllers/services/repositories, começando por admin.routes.js.

3.2 Estratégia de migração

  1. Extrair primeiro as funções compartilhadas de validação e normalização.
  2. Separar admin.routes.js em controller/service sem alterar o contrato HTTP.
  3. Extrair SQL para repositories e cobrir cada movimento com testes de integração.
  4. Separar a criação do app de listen() para permitir testes com Supertest.
  5. Migrar o frontend gradualmente para type="module"; não fazer uma reescrita total.

4. Qualidade de código e Clean Code

4.1 Melhorias prioritárias

  • SRP: src/routes/admin.routes.js mistura autenticação, parsing, validação, SQL e resposta. Dividir por recurso e camada.
  • DRY: centralizar texto(), parsing de IDs, paginação e respostas de erro.
  • Contratos: padronizar respostas ({ data, meta } para listas e { erro, codigo } para falhas).
  • Validação: usar schemas para rejeitar tipos inesperados, valores negativos, URLs inválidas e strings excessivas.
  • Nomenclatura: preservar o português no domínio, mas documentar uma convenção única para IDs, erros e nomes de arquivos.
  • Observabilidade: substituir logs livres por logger com níveis e contexto, sem registrar senhas, cookies ou dados sensíveis.

4.2 Pontos específicos

  • Em cursos.routes.js, a consulta de detalhe coordena quatro operações. Isso é aceitável funcionalmente, mas deve ficar em um service e pode usar Promise.all depois que a transação/consistência necessária for avaliada.
  • Evitar SELECT c.* em endpoints públicos; declarar campos reduz acoplamento e exposição acidental.
  • Adicionar paginação em listagens administrativas e públicas antes que o volume de dados cresça.
  • Extrair geração de slug para utilitário testável e tratar colisões explicitamente.

5. Segurança e performance

5.1 Segurança

Correção importante: o fallback de SESSION_SECRET em server.js é perigoso em produção. A aplicação deve encerrar a inicialização se o segredo não existir ou for fraco.
  1. Validar NODE_ENV, SESSION_SECRET e credenciais no startup.
  2. Aplicar express-rate-limit especificamente ao login e, se necessário, às rotas públicas de escrita.
  3. Adicionar proteção CSRF para operações autenticadas baseadas em cookie. Avaliar a estratégia adequada ao frontend antes de escolher uma biblioteca.
  4. Usar secure: true em produção com HTTPS e configurar trust proxy quando houver reverse proxy.
  5. Adicionar headers com helmet, incluindo política de conteúdo compatível com os componentes carregados.
  6. Validar URLs de documentos e imagens; não permitir esquemas perigosos como javascript:.
  7. Configurar rotação/expiração de sessão após login e regenerar o ID da sessão para reduzir session fixation.
  8. Manter o banco com usuário de menor privilégio; não usar root em produção.
  9. Adicionar secret scanning e revisar o histórico caso qualquer credencial real tenha sido versionada.

5.2 Performance

  • Adicionar índices para filtros e ordenações realmente usados, após verificar o schema e planos com EXPLAIN.
  • Adicionar paginação, limites máximos de busca e normalização do termo de pesquisa.
  • Usar Promise.all para consultas independentes do detalhe de curso, desde que não exista requisito de consistência transacional.
  • Não aumentar o pool de conexões arbitrariamente: medir concorrência, tempo de query e capacidade do MySQL antes de alterar connectionLimit.
  • Adicionar cache HTTP/ETag para conteúdo público e considerar Redis somente quando houver medição que justifique a complexidade.
  • Otimizar imagens e habilitar compressão/brotli no reverse proxy ou na aplicação.

6.1 Ordem de implementação

  1. Separar app de listen.
  2. Criar testes unitários sem banco para funções puras.
  3. Subir MySQL isolado para integração; executar schema e seed de teste.
  4. Testar primeiro os fluxos de maior risco: login, sessão, autorização, criação/moderação e XSS.
  5. Adicionar cobertura como indicador, não como objetivo isolado; priorizar comportamento crítico.

7. Ecossistema, DevOps e CI

7.1 Dependências e scripts

Adicionar, de forma incremental, ESLint, Prettier, Jest/Supertest, helmet, rate limiting e uma biblioteca de validação. Os scripts mínimos devem ser:

"lint": "eslint .",
"lint:fix": "eslint . --fix",
"format": "prettier --write .",
"format:check": "prettier --check .",
"test": "jest --runInBand",
"test:coverage": "jest --coverage",
"check": "npm run format:check && npm run lint && npm test"

7.2 Pipeline GitHub Actions

Criar .github/workflows/ci.yml acionado em pull requests e pushes na branch principal. O pipeline deve executar npm ci, format check, lint, testes, relatório de cobertura e auditoria de dependências. O MySQL deve ser um service container apenas nos jobs que realmente precisam dele.

7.3 Entrega e operação

  • Adicionar Dockerfile multi-stage e .dockerignore se Docker fizer parte do fluxo de deploy.
  • Adicionar GET /health sem dados sensíveis e, separadamente, um readiness check que valide o banco.
  • Definir migrações versionadas; não depender somente de executar schema.sql manualmente.
  • Adicionar Dependabot, CODEOWNERS, template de issue/PR e branch protection.
  • Documentar arquitetura, decisões, variáveis de ambiente, troubleshooting, API e política de deploy no README/docs.
  • Fixar versão de Node suportada e usar a mesma versão local, no CI e no container.

9. Checklist final para apresentação a recrutadores

  • ☐ CI verde em pull requests.
  • ☐ Lint, formatação e testes executáveis com um comando.

  • ☐ Segredos fora do Git e configuração validada no startup.
  • ☐ SQL parametrizado, validação de entrada e headers de segurança.
  • ☐ Migrations/seed reproduzíveis e banco de teste isolado.

10. Conclusão

O projeto não precisa de uma reescrita completa. A maior valorização para portfólio virá de demonstrar um ciclo profissional: configuração segura, validação, testes, revisão automática no CI e arquitetura que permita crescer sem colocar toda a lógica dentro das rotas. Implementar P0 e P1 já produzirá o maior ganho imediato; P2 e P3 devem ser executados conforme novas funcionalidades e necessidade real.

Este documento é uma recomendação técnica baseada na estrutura observada no repositório. Decisões como cache, tamanho do pool e Docker devem ser confirmadas por métricas, ambiente de hospedagem e requisitos de carga.
